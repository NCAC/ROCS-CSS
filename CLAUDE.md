# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

ROCS (Role-Oriented, One-Class CSS Semantics) is a CSS methodology specification and tooling project — not an application. The private root **rocs-monorepo** (`private: true`) uses pnpm workspaces `packages/*` ([pnpm-workspace.yaml](pnpm-workspace.yaml)), with independent package versions:

- [@rocss/rocs](packages/rocs/README.md) **1.0.0**: specification, CLI/JavaScript validator API, and Stylelint/ESLint configurations.
- [@rocss/sass-architecture](packages/sass-architecture/README.md) **0.1.0**: draft reference architecture documentation, generated from [scss-rocs-framework/](scss-rocs-framework/) without changing source contents, plus a heuristic static checker (`sass-architecture check`, [src/checker.js](packages/sass-architecture/src/checker.js)) for invariants I1–I3, I7–I11, I13, I16, I19, I22 and I23. No Sass mixins.
- [@rocss/sass](packages/sass/README.md) **0.1.0**: experimental Sass implementation, still `private: true` and unpublished pending test execution and contract review.
- Annotated [examples/](examples/).

**French ROCS documents in [docs/fr/](docs/fr/) are the source of truth.** Make normative changes there first, then update the corresponding [docs/en/](docs/en/) translation. Do not infer source paths from an obsolete `_FR.md` naming convention. Package documentation copies are generated by `pnpm run build` or `prepack`; **never edit those copies directly**. Packaging does not revise the specification or adopt proposals from the Sass review. See [docs/MONOREPO.md](docs/MONOREPO.md).

## Commands

```bash
pnpm install --frozen-lockfile  # Install dependencies from the root (Node.js >= 20, pnpm pinned by packageManager)
pnpm run build                  # Generate package documentation from canonical sources
pnpm test                       # Run repository tests, including Sass compilation, invalid arguments and installed archives
pnpm run lint                   # Run Stylelint (CSS/SCSS) + ESLint (JSX/TSX)
pnpm run lint:css               # Stylelint only
pnpm run lint:css:fix           # Stylelint with auto-fix
pnpm run lint:jsx               # ESLint only (JSX/TSX files)
pnpm run validate               # Run ROCS custom validator on ./examples
pnpm run validate:strict        # Same but exit 1 on warnings too
pnpm run validate:json          # Output validation report as JSON
pnpm run compile:examples       # Compile all example SCSS files to CSS
pnpm run check                  # build + test + lint + validate, in that order
pnpm run pack:check             # Inspect all three archives, including the private workspace, with pnpm pack --dry-run; no publication
```

To compile a single example's SCSS:

```bash
pnpm exec sass examples/ProductCard/styles.scss examples/ProductCard/styles.css
```

To validate a specific directory:

```bash
node tools/rocs-validate.js --dir ./examples --format github
node tools/rocs-validate.js --dir ./src --format json --output report.json
```

The legacy commands above remain supported through the wrapper in [tools/rocs-validate.js](tools/rocs-validate.js). After installation, the workspace CLI is also available with `pnpm exec rocs --dir ./examples`.

## Architecture

- [docs/fr/](docs/fr/): canonical French ROCS specification and companion documents; [docs/en/](docs/en/): English translations.
- [packages/rocs/src/validator.js](packages/rocs/src/validator.js): validator implementation and exported API (`analyzeHtml`, `analyzeScss`, `validateRocsClass`, `runCli`). Importing the module does not launch the CLI; `runCli` terminates the process, so use the analysis functions for integrations.
- [packages/rocs/bin/rocs.js](packages/rocs/bin/rocs.js): package CLI entry point; [tools/rocs-validate.js](tools/rocs-validate.js): compatibility wrapper only.
- [packages/rocs/stylelint.config.json](packages/rocs/stylelint.config.json) and [packages/rocs/eslint.config.js](packages/rocs/eslint.config.js): actual lint configurations. The ESLint rules and regex live in [packages/rocs/eslint-plugin.js](packages/rocs/eslint-plugin.js) (exported as `@rocss/rocs/eslint-plugin`); `eslint.config.js` only enables them on JSX/TSX, with no ESLint core rules. The root [.stylelintrc.json](.stylelintrc.json) and [eslint.config.js](eslint.config.js) delegate to them. ESLint targets JSX; TypeScript and other syntaxes require appropriate parser setup.
- [scss-rocs-framework/](scss-rocs-framework/): canonical Sass architecture draft documents, not an implemented framework.
- [packages/sass/](packages/sass/): canonical implementation of the combinators layer, with 13 SCSS files copied/adapted from the initial local import directory. The initial import directory has been removed: `packages/sass` is the only source. The package includes an [actual MIT license copy](packages/sass/LICENSE), not a generated documentation artifact.
- [tools/build-package-docs.js](tools/build-package-docs.js): generates documentation copies for the two publishable packages; do not edit package documentation copies.
- [examples/](examples/): annotated HTML/SCSS/CSS examples; [tests/](tests/): repository tests.

**Combinator API:** seven implemented mixins: `context.media`, `context.supports`, `context.container`, `state.pseudo-class`, `state.attribute`, `scope.ancestor`, and `part.pseudo-element`. Import families with `@use "pkg:@rocss/sass/context"`, `/state`, `/scope`, or `/part`, using Dart Sass ≥ 1.71.0 with the Node package importer (CLI: `--pkg-importer=node`; API: `importers: [new NodePackageImporter()]`, passing an entry directory when there is no entry script). `loadPaths: ["node_modules"]` with unprefixed `@use "@rocss/sass/..."` remains a supported alternative. After `pnpm install`, imports resolve the local workspace (linked at the root through `workspace:*` devDependencies), not a published package. Use family entry points rather than the aggregate entry point when a layer is restricted to a family (I23). Naming convention (architecture §0.3): framework/built-in mixins are kebab-case like `sass:list` (`state.pseudo-class`); concrete project mixins are snake_case (`from_wide`, `flex_between`). Sass treats `-` and `_` as equivalent, so this is a readability convention, not compiler-enforced.

**Test status:** added tests cover Sass entry-point and composition compilation, invalid arguments, and installation of all three local archives outside the repository, including compilation from the installed package. Their presence is not evidence of execution or success; run them and review contracts before changing experimental/private status.

**Validator scope:** CSS was added to the scanned extensions, alongside HTML, HTM and SCSS. Both SCSS sources and generated CSS are analyzed separately. Analysis is heuristic, not a complete compliance proof; the CLI has no template adapters for Twig, Vue, JSX, etc., and semantic decisions still require human review. Moving tooling into a package does not change the business rules below.

## Release status

No package has been published; packages will be published under the `@rocss` npm organization, which the project owns (https://www.npmjs.com/org/rocss). Root release scripts were removed because the old global release flow does not fit independently versioned packages. Any future publication is manual from the repository, after `pnpm run check`, `pnpm run pack:check`, archive review, and verification of npm authentication and scope permissions. There is no CI publication. The root and the `sass` workspace remain private; `@rocss/sass` stays experimental at **0.1.0** pending test execution and contract review. `pack:check` inspects all three archives (`@rocss/rocs`, `@rocss/sass-architecture`, and `@rocss/sass`) without publishing. `private: true` prevents publication, not local archive creation with `pnpm pack`.

## The ROCS methodology (essential rules for working in this repo)

**Naming**: Block = `PascalCase` (e.g. `ProductCard`), Element = `Block-camelCase` (e.g. `ProductCard-title`, `ProductCard-headerBadge`). Max 4 PascalCase segments in a Block name, max 3 camelCase segments in an Element name.

**One class per element**: an HTML element may have 0 or 1 ROCS class. No composition in HTML.

**`data-*` attributes**: reserved exclusively for JS-driven dynamic state/parameters. Decisive test: *"Can the value change client-side?"* — if no, it must be a ROCS class, not a `data-*` attribute.

| `data-*` usage | ROCS compliant? |
| --- | --- |
| Dynamic state driven by JS | ✅ |
| Contextual metadata (layout/config, modifiable client-side) | ✅ with `:where()` |
| Static semantic variant (`data-type="book"`) | ❌ → use `ProductCardBook` class |
| Design system variant (`data-variant="primary"`) | ❌ → compose in CSS |
| Pure JS hook (analytics, testid) | ✅ but never target in CSS |

**`id` in CSS**: forbidden. IDs are for JS targeting and anchors only.

**Forbidden generic Block names**: `Button`, `Btn`, `Modal`, `Dialog`, `Card`, `Input`, `Select`, `Checkbox`, `Radio`, `Toggle`, `Badge`, `Alert`, `Toast`, `Tooltip`, `Dropdown`, `Menu`, `Tabs`, `Accordion`, `Spinner`, `Loader`, `Skeleton`, `Avatar`, `Icon`, `List`, `Table`, `Form`, `Header`, `Footer`, `Sidebar`, `Nav`, `Breadcrumb`, `Pagination`, `Slider`, `Carousel`, `Grid`, `Page`. Use applicative names instead (e.g. `ProductCard-cta` instead of `Button`).

**Exception**: a ROCS class combined with a framework class is allowed: `class="ProductCard v-cloak"` — only the ROCS class is governed by these rules.

**Cascade**: selectors must be self-contained (specificity 0,1,0). Two allowed exceptions:

1. Block with dynamic state targeting its own elements: `.Block[data-state="x"] .Block-element { }`
2. Global context with mandatory `:where()`: `body[data-theme="dark"] :where(.Block-element) { }`

Cross-block cascade (`.Sidebar .ProductCard { }`) is always forbidden.

**Selector rules summary**:

| Selector | Allowed? |
| --- | --- |
| `.ClassName { }` | ✅ |
| `.ClassName:hover`, `.ClassName::before` | ✅ |
| `.ClassName[aria-expanded]`, `.ClassName[data-state]` | ✅ |
| `.Block[data-x] :where(.Block-element)` | ✅ max 2 levels |
| `body[data-theme] :where(.Block)` | ✅ with `:where()` |
| `.Block .Block-element { }` | ❌ useless cascade |
| `.Sidebar .ProductCard { }` | ❌ cross-block cascade |
| `.Block > .Element`, `.El + .El2` | ❌ |
| `#id { }` | ❌ never |

**Style composition**: done in CSS via mixins (`@include`), never via utility classes in HTML.

**Element → Block promotion**: promote when the element has ~3+ styled descendants, is reused across multiple Blocks, or carries autonomous logic/state. Before: `ProductGallery-header` → After: `ProductGalleryHeader`.

**Anti-patterns to detect**:

| Anti-pattern | Example | Fix |
| --- | --- | --- |
| Utility classes in HTML | `class="flex p-4 text-lg"` | Compose in CSS |
| BEM modifier | `class="Block--modifier"` | Native attrs / dynamic `data-*` |
| State classes | `class="Nav is-open"` | `data-state="open"` or `aria-expanded` |
| `id` in CSS selectors | `#header { }` | ROCS class |
| Static `data-*` for variant | `data-type="book"` in CSS | Class `ProductCardBook` |
| Descendant selectors | `.Block .Element { }` | Self-contained `.Element { }` |
| Element depth > 3 | `-headerTitleBadgeIcon` | Promote to Block |
| Generic DS Block | `Button`, `Modal`, `Card` | Applicative name |

## Regex (must be identical across all tooling files)

```text
^[A-Z][a-zA-Z0-9]*(?:-(?:[a-z]+[0-9]*)(?:[A-Z][a-z]+[0-9]*){0,2})?$
```

This regex is used in [packages/rocs/stylelint.config.json](packages/rocs/stylelint.config.json) (`selector-class-pattern`), [packages/rocs/eslint-plugin.js](packages/rocs/eslint-plugin.js), and [packages/rocs/src/validator.js](packages/rocs/src/validator.js). Keep these three sources synchronized and update relevant tests when changing it. The root configs and historical CLI wrapper do not own regex definitions.

## Adding or modifying examples

Each example in `examples/` requires:

- `index.html` — uses only ROCS classes (0 or 1 per element)
- `styles.scss` — all style composition via mixins, no utility classes
- `README.md` — documents the ROCS design choices made

After editing SCSS, recompile: `pnpm exec sass examples/ComponentName/styles.scss examples/ComponentName/styles.css`

Then run `pnpm run check` (build → test → lint → validate) and `pnpm run pack:check` before submitting. Do not treat a clean heuristic validator report as proof of full ROCS compliance.

## Editing the specification

When editing any normative content in [docs/fr/SPECIFICATION.md](docs/fr/SPECIFICATION.md):

- Always cite the section number (`§3.2`, `§6.2.1`, etc.)
- Use the normative language convention: **DOIT / NE DOIT PAS** (absolute), **DEVRAIT / NE DEVRAIT PAS** (strong recommendation), **PEUT** (permitted option)
- Each new rule needs: normative statement + ✅ compliant example + ❌ non-compliant example + informative justification
- Verify the new rule does not contradict an existing one
- After any normative change, check whether [packages/rocs/stylelint.config.json](packages/rocs/stylelint.config.json), [packages/rocs/eslint-plugin.js](packages/rocs/eslint-plugin.js), and [packages/rocs/src/validator.js](packages/rocs/src/validator.js) need updating to match; update tests as appropriate

When a spec section changes, these files may need updating: the paired EN translation, `CHEATSHEET`, `GLOSSARY`, `MIGRATION_GUIDE`, `IMPLEMENTATION_GUIDE`, and all three tooling files.

## Language policy

For ROCS documentation, use the paired [docs/fr/](docs/fr/) and [docs/en/](docs/en/) trees, not `_FR` filename variants. The root [README_FR.md](README_FR.md) and [README.md](README.md) are the French/English overview pair.
